# 本地工作台 UI 设计评审

评审日期：2026-11-07。范围：独立面板的对话、管理首页、实时执行与现有管理页；结合源码审查和本工单验证，不包含后端安全审计。

## 结论

工作台的主任务应是“发出指令 → 阅读回复 → 处理需要我的事项 → 必要时查看执行细节”。原布局把高频对话藏在弹窗里，把大块执行过程放在所有操作之前，与这个任务顺序相反。这次按使用频率调整信息层级，保留现有六个管理页、设计 token 和业务概念。

## 本次落实

| 问题 | 调整 | 验收要点 |
| --- | --- | --- |
| 草稿仅存在组件内存 | 文字与回复目标逐次同步写入 localStorage，图片独立存入 IndexedDB；各话题互相隔离，恢复当前话题、发送者及自动接单设置 | 立即刷新、关闭重开、图文恢复、话题切换、失败保留、成功清空 |
| 对话入口藏在按钮后 | 本地对话直接置顶；输入和历史无需打开弹窗 | 初次进入即可输入，无二级菜单 |
| 执行过程占据首屏 | 本地对话 → 管理操作 → 实时执行；顶部提供三个区域的直达链接 | DOM 与视觉顺序一致，键盘可直达 |
| 内部管理字段抢占注意力 | 对话 ID、发送者 ID、自动接单放入折叠设置；新建话题保持一键可用 | 默认集中在内容而非内部标识 |
| 保存状态不明确 | 显示图片恢复/保存进度及存储失败；发送失败保留草稿 | 存储不可用时不能虚报已保存 |
| 对话回看和发送不顺手 | 回复后聚焦输入、回到最新消息、Ctrl/Cmd + Enter 发送，保留普通 Enter 换行及输入法合成行为 | 回看不会被新消息强行拉走，发送操作可发现 |
| 运行状态过度依赖小图标 | 执行状态增加可见文字，工具详情默认折叠 | 运行状态可读，详细过程按需展开 |

保存范围是当前浏览器及同一站点路径，不是账户同步；切换设备、浏览器、域名或端口不会共用草稿，清除站点数据会删除草稿。图片走 IndexedDB，避免把允许的 12 MiB 图片草稿塞进容量较小的文字存储。保存错误必须留在页面上，让用户保留原文或原图后再刷新。

## 整体设计意见与后续顺序

### P0

本轮静态 UI 审查未发现可确认的 P0；这不替代运行态或安全审计。

### P1：先补齐合并操作的可预期性

`src/client/ticket-activity.tsx` 的“立即合并 / 合并并推送”直接执行请求，并固定传入 `commitDirty: true`。用户无法在操作前核对将自动提交哪些改动、目标分支和是否推送。建议下一步增加具体确认内容及待提交文件范围，文案明确自动提交行为，遵循 `005-panel.md` 已有的破坏性操作确认原则。本工单不改动该业务流程。

### P2：让恢复能力可发现

1. **最近话题与草稿入口。** 现有话题仍靠 ID 切换。下一步提供最近话题、可读标题和“有未发送草稿”标记，让恢复不依赖记住内部 ID；先做可返回的列表，再考虑搜索。
2. **区分两种跟随。** `standalone-activity.tsx` 中“自动选择运行中的工单”和“跟随本会话最新消息”是两种行为。当前停止滚动跟随并不阻止父组件切换到另一运行工单。建议显式显示自动/固定模式，回看时固定当前会话，并提示未读消息。
3. **统一因果时间线。** 实时回复与工具目前分别滚动，顺序也不同。建议按时间排列在同一活动流中，将工具组合折叠，保留完整调试入口，使用户能把说明、操作与结果对应起来。
4. **补齐增量消息的辅助技术提示。** 对话历史目前有区域名称，但没有新增消息的 log 语义。应只通知新增消息/新回复完成，不要让读屏软件每秒重复整段流式输出。
5. **统一子标签键盘交互。** `eval.tsx` 的部分 tablist 尚未与主导航一样支持方向键、roving tabindex 和面板关联，后续复用现有控件行为。
6. **区分整页与内嵌卡片版式。** `ticket-activity.tsx` 复用 `.dt-live-workspace`，会继承整页的缩宽与外边距。后续增加局部内嵌变体，并用截图核对，避免修改全局 token 牵动其他页。

保留 `overview.tsx` 的“待人工 → 问题 → 最近回复 → 历史统计”顺序。统计帮助理解系统，不能再次挤占需要人的操作。暂不重做配色、圆角和所有管理页；先解决入口、反馈、恢复和操作的可预期性。

## 同类产品参考

以下来自官方资料，借鉴的是任务组织方式，不是照搬外观：

- [Linear Issue Drafts](https://linear.app/changelog/2023-05-11-issue-drafts)：完整保存标题、描述和属性，并提供草稿入口。对这里的启发是保存上下文且能找回；本项目这次明确采用浏览器本地保存，不承诺 Linear 的账户级同步。
- [Linear Inbox](https://linear.app/docs/inbox)：Priority 默认集中需要注意的更新。对应本项目管理首页继续优先待人工与问题，避免普通健康统计和流水日志抢占操作位置。
- [Cursor Agent](https://cursor.com/help/ai-features/agent)：从 Agent 面板直接输入请求，执行中可继续给出后续消息、查看变更。这里采用直接可见的对话入口，把执行详情作为辅助阅读区域。
- [Cursor Side Chats and Conversation Search](https://cursor.com/changelog/side-chat)：持久对话可再次访问，支持会话与会话内搜索。适合指导下一步的最近话题与历史找回。
- [MDN Storage quotas and eviction criteria](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)：浏览器存储有配额且可能抛错。文字与大附件分开存储，并提供失败反馈，是本次恢复机制的技术依据。

推荐后续顺序：合并操作确认 → 最近话题与草稿入口 → 固定会话与新消息提示 → 统一时间线 → 辅助技术、键盘及内嵌样式完善。
